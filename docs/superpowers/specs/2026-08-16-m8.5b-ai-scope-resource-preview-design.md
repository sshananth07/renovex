# M8.5B-A — AI Scope & Resource Preview Design

**Date:** 2026-08-16  
**Product:** Renovex / Renovation Project Intelligence Platform  
**Milestone:** M8.5B-A — AI Scope + Resource Preview  
**Status:** Approved design, pending implementation-plan review  

---

## 1. Purpose

M8.5B-A introduces the first contractor-facing AI workflow into Renovex after the deterministic Phase 1 commercial/procurement system and M8.5A frontend/E2E closure.

This milestone is intentionally a narrow preview of the later M10 AI Assistance milestone. Its purpose is to prove a safe, reusable AI architecture and a complete contractor-facing vertical slice without allowing an LLM to become authoritative for project structure, quantities, costs, pricing, procurement, or financial calculations.

The operating principle is:

```text
AI suggests.
The system calculates.
The contractor approves.
```

M8.5B-A must prove that AI can accelerate scope setup and resource planning while preserving the existing Renovex domain model, tenancy guarantees, deterministic calculations, and explicit human review.

---

## 2. Scope

### 2.1 In scope

M8.5B-A includes three connected AI stages:

1. **AI Space Assistant**
   - Contractor enters a whole-project renovation brief.
   - AI proposes Spaces/rooms/areas.
   - Contractor accepts, edits and accepts, or rejects each suggestion.
   - Accepted suggestions immediately create real `Space` domain objects through existing Go services.

2. **AI Work Item Assistant**
   - Runs only after Spaces have been reviewed and confirmed.
   - AI proposes Work Items against confirmed Space IDs or as project-level/unassigned work.
   - Suggestions are classified as explicit scope, supporting scope, or possible missing scope.
   - Contractor accepts, edits and accepts, or rejects each suggestion.
   - Accepted suggestions immediately create real `WorkItem` domain objects through existing Go services.

3. **AI Resource Assistant**
   - Runs as a project-level batch against confirmed Work Items.
   - AI may suggest Materials, Trades, and Equipment.
   - Contractor reviews each suggestion.
   - Approved suggestions are automatically attached to the relevant Work Item as real planning data.
   - Existing Materials may be linked; unmatched Materials may be created through the normal Material domain flow and then attached.

The milestone also includes:

- Python FastAPI AI service.
- Gemini provider implementation through the official `google-genai` SDK.
- Deterministic mock AI provider for tests and offline development.
- Go orchestration, persistence, authorization, idempotency and domain mutation.
- AI generation batches and AI suggestion lifecycle.
- A lightweight `WorkResourceRequirement` planning-domain model.
- Full Next.js review/approval UI.
- Generated OpenAPI integration.
- Automated tests across Python, Go and Next.js.
- Deterministic end-to-end acceptance with the mock provider.
- A real Gemini smoke test using synthetic/non-sensitive renovation data.

### 2.2 Explicitly out of scope

M8.5B-A does not implement:

- AI quotation writing.
- AI project reports.
- AI project copilot.
- Photo summarization.
- Computer-vision defect detection.
- Structural or compliance diagnosis.
- AR/LiDAR.
- Digital twin generation.
- Construction-accurate rendering.
- Blueprint reconstruction.
- AI-generated authoritative quantities.
- AI-generated material prices.
- AI-generated labour rates.
- AI-generated cost totals.
- Automatic CostItem creation from AI resource approval.
- Automatic Estimate/Quotation changes from AI approval.
- Purchase Orders.
- Award -> committed Cost automation.

Those capabilities remain later milestones or later M10 slices.

## 4. Architecture

### 4.1 Runtime architecture

```text
                    Contractor
                        │
                        ▼
                  Next.js Web App
                        │
                        ▼
                 Go + Huma Backend
                 ─────────────────
                 • Authentication
                 • Tenant isolation
                 • Project authorization
                 • Authorized-context selection
                 • AI batch/suggestion persistence
                 • Domain validation
                 • Accepted-suggestion application
                        │
                  internal HTTP
                        ▼
               Python FastAPI AI Service
                 ─────────────────
                 • Request validation
                 • Prompt construction
                 • Structured output schemas
                 • Provider abstraction
                        │
                        ▼
                  AIProvider interface
                     ├─ GeminiProvider
                     └─ MockProvider
```

### 4.2 Hard boundaries

- The browser never calls Python directly.
- Python has no direct MongoDB access.
- Python has no authority to create Spaces, WorkItems, Materials, WorkResourceRequirements, CostItems, Estimates, Quotations, RFQs, Supplier Offers, Awards, or financial records.
- Go remains the authoritative public API and tenant/domain boundary.
- Go selects the exact context sent to Python.
- Gemini receives only the context required for the current operation.
- Accepted suggestions are applied only through existing deterministic Go domain services or narrowly added domain services.
- Gemini API credentials exist only in the Python service.

### 4.3 Repository layout

Target structure:

```text
apps/web/        # Next.js contractor UI
backend/         # Go + Huma authoritative API/domain
ai-service/      # Python + FastAPI, AI only
```

No second browser-facing API is introduced.

Python exposes operation-oriented orchestration functions independent of Gemini:

```text

suggest_work_items()
suggest_resources()
```

Provider boundary:

```text
AIProvider
├── GeminiProvider
└── MockProvider
```

Configuration is environment-driven:

```env
AI_PROVIDER=gemini
GEMINI_API_KEY=...
GEMINI_MODEL=...
```

Tests and offline development use:

```env

```

The provider implementation must be replaceable without changing Renovex's business-domain contracts.

Gemini free-tier usage is development-only for synthetic/non-sensitive renovation data. Production provider/data-handling decisions are deferred to a later production-readiness milestone.

## 6. Contractor Project Brief

The project needs a reusable contractor-authored scope description. Add a normal project-domain field:

```text
Project.ScopeBrief
```

This is not AI output. It is authoritative contractor-authored descriptive project context.

Example:

```text
Full renovation of a 3-bedroom condominium. Redo the kitchen and two
bathrooms, replace flooring in all bedrooms and the living area, and repaint
the whole unit.
```

Future AI features may reuse this field, but no AI result may silently rewrite it.

## 7. AI Generation Batch

Each generation request is represented by a durable batch record.

Conceptual model:

```text
AIGenerationBatch

id
companyId
projectId

type:
  space_suggestions
  work_item_suggestions
  resource_suggestions

status:
  processing
  completed
  failed

operationId
provider
model
promptVersion
schemaVersion

inputRevision
inputFingerprint

startedAt
completedAt?
failedAt?
errorCode?

createdBy
createdAt
```

### 7.1 Purpose

The batch provides:

- generation provenance;
- provider/model/prompt tracking;
- input-state traceability;
- idempotency support;
- regeneration history;
- clean failure tracking;
- future compatibility with asynchronous jobs without redesigning suggestions.

### 7.2 Input fingerprint

The input fingerprint must be deterministic over the authoritative inputs relevant to the generation type.

Examples:

**Space generation:**

```text
project scope brief
+
existing Space identities / relevant revisions
```

**Work generation:**

```text
project scope brief
+
confirmed Space IDs / relevant revisions
+
existing confirmed Work Items / relevant revisions
```

**Resource generation:**

```text
confirmed Work Items / relevant revisions
+
existing WorkResourceRequirements
+
provided Material catalog candidates
```

A generation remains historical when project state changes. New state produces a new generation batch rather than rewriting the old one.

## 8. AI Suggestion

AI output remains separate from authoritative business data until contractor approval.

Conceptual model:

```text
AISuggestion

id
companyId
projectId
batchId

type:
  space
  work_item
  material_resource
  trade_resource
  equipment_resource

status:
  pending
  accepted
  modified
  rejected

confidence?
rationale?
suggestedData
inputFingerprint

acceptedDomainObjectId?
acceptedAt?
acceptedBy?

rejectedAt?
rejectedBy?

revision
createdAt
updatedAt
```

Only a short contractor-facing rationale is stored. Hidden provider reasoning/chain-of-thought is never requested as a business record and never stored.

### 8.1 Review lifecycle

```text
                    pending
                  /    |    \
                 /     |     \
          accepted  modified  rejected
              |        |
              └────┬───┘
                   ↓
          authoritative object
```

- **Accept:** create authoritative domain object using suggestion as presented.
- **Edit & Accept:** contractor edits allowed fields, then authoritative object is created from contractor-confirmed values; suggestion becomes `modified`.
- **Reject:** create nothing; suggestion becomes `rejected`.

The original AI proposal remains available for provenance even when modified.

## 9. AI Space Assistant

### 9.1 Input

Go sends only:

- project ID;
- contractor scope brief;
- existing Space IDs, names and types required for duplicate avoidance.

Example internal request:

```json
{
  "operationId": "op_123",
  "project": {
    "id": "project_123",
    "scopeBrief": "Full renovation of a 3-bedroom condominium..."
  },
  "existingSpaces": [
    {
      "id": "space_existing",
      "name": "Kitchen",
      "type": "kitchen"
    }
  ]
}
```

### 9.2 Output

Space suggestions intentionally remain narrow:

```json
{
  "suggestions": [
    {
      "name": "Master Bathroom",
      "spaceType": "bathroom",
      "rationale": "Bathroom renovation is explicitly mentioned.",
      "confidence": 0.94
    }
  ]
}
```

The schema does not permit AI-supplied:

- dimensions;
- floor areas;
- measurements;
- quantities;
- costs;
- material requirements;
- financial values.

### 9.3 Acceptance

Acceptance is a single Go-owned operation:

```text
POST /ai-suggestions/{id}/accept
```

Go:

1. validates tenant/project ownership;
2. validates suggestion is still pending;
3. revalidates against current project state;
4. checks likely Space duplication;
5. calls the existing Space domain service;
6. creates the real Space;
7. records suggestion acceptance/provenance;
8. returns the resulting domain object.

The browser does not independently create a Space and then separately mark a suggestion accepted.

## 10. AI Work Item Assistant

### 10.1 Preconditions

Work Item generation is unlocked once Space review has produced at least one confirmed Space. The contractor does not need to accept every suggested Space.

Existing manually created Spaces are equally valid and must be included.

### 10.2 Input

Go sends:

- project scope brief;
- confirmed Spaces with real IDs;
- existing Work Items relevant to duplicate avoidance.

Example:

```json
{
  "operationId": "op_456",
  "projectBrief": "...",
  "spaces": [
    {
      "id": "space_123",
      "name": "Kitchen",
      "type": "kitchen"
    }
  ],
  "existingWorkItems": [
    {
      "id": "work_1",
      "spaceId": "space_123",
      "description": "Remove existing cabinets",
      "workType": "demolition"
    }
  ]
}
```

### 10.3 Output fields

Each Work Item suggestion contains:

```text
description
workType
scopeLevel
spaceId
scopeOrigin
rationale
confidence
```

`scopeLevel`:

```text
space
project
```

`scopeOrigin`:

```text
explicit_scope
supporting_scope
possible_missing_scope
```

### 10.4 Space vs project-level work

Rules:

```text
scopeLevel = space
→ spaceId MUST be one of the confirmed IDs supplied by Go

scopeLevel = project
→ spaceId MUST be null
```

Project-level/unassigned Work Items are permitted for legitimate cross-project work such as:

- site protection;
- general debris disposal;
- temporary works;
- whole-unit preparation;
- final post-construction cleaning.

No synthetic "Whole Property" Space is created merely to attach these items.

### 10.5 Missing-scope intelligence

Missing-scope detection is part of the same Work Item generation pass. The UI must distinguish:

- work explicitly requested by the contractor;
- supporting work the AI believes is needed to deliver the requested scope;
- possible missing scope the contractor may have omitted.

All three remain equally non-authoritative until reviewed.

### 10.6 Acceptance

The contractor may edit:

- description;
- work type;
- Space assignment;
- Space-scoped vs project-level assignment.

On acceptance, Go revalidates all lineage against current tenant/project state and calls the existing WorkItem service.

No AI suggestion supplies authoritative WorkItem quantity or cost information in this milestone. If the current WorkItem create contract requires contractor-owned fields such as quantity and unit, the acceptance UI must require the contractor to enter or confirm those fields before the WorkItem is created. The AI response schema must not populate them, and the backend must reject acceptance until all existing WorkItem invariants are satisfied.

## 11. WorkResourceRequirement Domain

A lightweight planning layer is introduced so approved AI resource suggestions have a real domain destination before costing/procurement begins.

Conceptual model:

```text
WorkResourceRequirement

id
companyId
projectId
workItemId

resourceType:
  material
  trade
  equipment

materialId?       # material only
name

status:
  confirmed

source:
  manual
  ai_suggestion

sourceSuggestionId?
createdBy
createdAt
updatedAt
schemaVersion
```

### 11.1 Meaning

The entity means only:

> This Work Item is expected to require this resource.

It does not mean:

- a material quantity has been determined;
- a worker has been selected;
- a labour rate has been selected;
- an equipment rate has been selected;
- a supplier has been chosen;
- a CostItem exists;
- procurement demand exists;
- a commercial commitment exists.

### 11.2 No AI financial authority

`WorkResourceRequirement` contains no authoritative cost fields in M8.5B-A.

Quantity is also excluded initially from this planning object. Deterministic/manual downstream flows remain responsible for quantities, rates, prices, waste, conversions and CostItems.

This preserves:

```text
WorkItem
   ↓
WorkResourceRequirement
   ↓
contractor/deterministic quantity + rate/price
   ↓
CostItem / procurement demand
```

## 12. AI Resource Assistant

### 12.1 Execution style

Resource generation is project-level batch generation after Work Items are confirmed.

The contractor clicks a single action such as:

```text
Suggest Resources
```

Go collects confirmed Work Items and allowed supporting context, then makes one AI generation request.

This avoids one LLM call per Work Item, provides project-wide context, and simplifies duplicate detection/review.

### 12.2 Supported resource types

M8.5B-A AI may suggest:

```text
material
trade
equipment
```

Subcontractor and transport suggestions are explicitly deferred from M8.5B-A.

### 12.3 Material catalog context

Python must not search Renovex's database.

Go retrieves relevant Material catalog candidates before the AI request and sends only the approved candidate data needed by the model.

A returned `candidateMaterialId` is advisory only. The contractor still chooses whether to use that Material, select a different Material, create a new Material, or reject the suggestion.

### 12.4 Existing Material

```text
AI suggests Tile Adhesive
        ↓
possible Material catalog match
        ↓
contractor chooses Use Existing
        ↓
Go creates WorkResourceRequirement
linked to selected materialId
```

### 12.5 New Material

```text
AI suggests Tile Spacers
        ↓
no desired catalog match
        ↓
Create & Add
        ↓
normal contractor-controlled Material form
        ↓
Material service creates Material
        ↓
WorkResourceRequirement created automatically
```

The AI-suggested name may prefill the Material form, but contractor-required catalog fields remain contractor controlled.

### 12.6 Trade

AI may suggest a trade such as `Tiler`, `Plumber`, or `Painter`.

Acceptance creates a confirmed trade requirement only.

It must not automatically:

- create/select a Worker;
- create a LabourEntry;
- choose a worker rate;
- choose a project labour rate;
- calculate labour cost.

### 12.7 Equipment

AI may suggest equipment such as a tile cutter.

Acceptance creates a confirmed equipment requirement only. It does not create rental/purchase costs automatically.

## 13. Internal Go <-> Python API

Use three explicit internal operations rather than one generic generation endpoint:

```text
POST /internal/v1/spaces/suggest
POST /internal/v1/work-items/suggest
POST /internal/v1/resources/suggest
```

This keeps schemas, prompt policies, tests and future evolution isolated by capability.

The internal API is not part of the browser/public Huma OpenAPI surface.

## 14. Structured Output

Gemini must use provider-supported structured output mapped to Pydantic schemas.

The service must not rely on:

- parsing prose;
- stripping Markdown JSON fences;
- regex extraction of arbitrary JSON;
- guessing missing fields;
- repairing malformed AI responses into authoritative data.

Flow:

```text
Gemini
  ↓
structured-output schema
  ↓
Pydantic validation
  ↓
valid response OR controlled generation failure
```

Python validates the model response before returning it.

Go then performs its own domain/tenant/lineage validation again. Python output is untrusted from the business-domain perspective.

---

## 15. Go Domain Revalidation

Go must revalidate every foreign reference returned by Python.

Examples:

```text
spaceId
→ belongs to authenticated Company
→ belongs to current Project
→ remains an eligible current Space

workItemId
→ belongs to authenticated Company
→ belongs to current Project

candidateMaterialId
→ belongs to authenticated Company catalog
```

A malformed or malicious AI response must not be able to cross tenant boundaries or reference unrelated resources.

## 16. Generation Execution Model

M8.5B-A uses synchronous generation:

```text
Browser
→ Go
→ Python
→ Gemini
→ Python validates
→ Go validates + persists
→ Browser receives suggestions
```

Reasoning:

- simplest preview architecture;
- easiest contractor UX;
- avoids premature queue/polling infrastructure;
- generation batches already preserve a future migration path to background jobs.

Do not introduce SQS/durable workers in this milestone.

---

## 17. Generation Atomicity

A generation batch is all-or-nothing at suggestion persistence time.

Correct behavior:

```text
AI response fully received
→ entire output schema validates
→ Go validates complete suggestion set
→ persist complete batch/suggestions
```

Failure behavior:

```text
processing
→ failed
```

A failed generation creates zero partially usable AI suggestions.

Bulk contractor acceptance is different: each selected suggestion is independently governed, so a bulk action may report partial success while failed items remain pending.

## 18. Idempotency

### 18.1 Generation

Each generation request has an `operationId` plus an input fingerprint.

Rules:

```text
same operationId + same fingerprint
→ same logical generation / safe retry

same operationId + different fingerprint
→ conflict
```

This protects ambiguous network retries from creating duplicate batches.

### 18.2 Suggestion acceptance

Acceptance is idempotent.

Authoritative objects created by AI-suggestion acceptance carry a nullable `sourceSuggestionId` provenance field. For domain models that already expose a `source` field, it is set to `ai_suggestion`. In M8.5B-A this applies to AI-created `Space`, `WorkItem`, contractor-confirmed `Material` created through the Resource Assistant's Create & Add flow, and `WorkResourceRequirement`. Each affected collection enforces a sparse unique index on `sourceSuggestionId`.

```text
sourceSuggestionId = <AISuggestion ID>
source = ai_suggestion   # where the domain already has a source concept
```

This stable provenance key is the acceptance idempotency anchor. If a process/network failure happens after domain creation but before the `AISuggestion` is marked accepted, retrying the acceptance must detect/load the already-created object by `sourceSuggestionId`, repair the suggestion's accepted state, and return that same object instead of creating another.

Retrying an already completed acceptance returns the already-created result.

## 19. Stale Suggestions

Suggestions may become stale between generation and review.

Acceptance always validates current project state, not only generation-time state.

Examples:

- AI suggested a Kitchen, but the contractor manually created Kitchen before accepting.
- AI Work Item references a Space that was archived/changed.
- AI Resource suggestion references a Work Item that is no longer eligible.

If the suggestion cannot be safely applied:

```text
409 Conflict
```

The public UI message should explain that the suggestion was generated from an older project state and should be reviewed/regenerated. Internal fingerprint/revision details remain implementation/logging concerns.

A stale suggestion is never silently repaired into a different authoritative object by the backend.

---

## 20. Duplicate Handling

AI prompts should include existing project state and instruct the model to avoid obvious duplicates, but prompt behavior is not a correctness mechanism.

### 20.1 Spaces

Use deterministic normalized comparisons on name/type to detect likely existing Spaces.

An AI Space suggestion that now collides with a real current Space should not silently create another Space.

### 20.2 Work Items

Do not impose hard uniqueness on WorkItems because legitimate renovation work may be similar.

Use advisory duplicate detection based on current Space/project scope and normalized descriptive fields. Contractor may explicitly accept anyway when the domain permits it.

### 20.3 Resources

Resource duplicate checks may be stricter:

```text
same WorkItem
+
same resourceType
+
same materialId
```

or for unlinked resources:

```text
same WorkItem
+
same resourceType
+
normalized name
```

Repeated clicks must not create duplicate identical requirements.

## 21. Internal Service Security

### 21.1 Go -> Python authentication

M8.5B-A uses a shared internal service credential:

```text
Authorization: Bearer <AI_INTERNAL_TOKEN>
```

Go config:

```env
AI_SERVICE_URL=http://localhost:8090
AI_INTERNAL_TOKEN=...
```

Python config:

```env
INTERNAL_API_TOKEN=...
```

Rules:

- token exists only in backend and AI-service runtime configuration;
- token never reaches Next.js;
- token is not stored in MongoDB;
- token is not included in public OpenAPI;
- token is not sent to Gemini;
- Python rejects unauthenticated direct requests;
- Python does not expose permissive browser CORS.

Production may later replace the shared token with stronger service identity/mTLS/cloud IAM without changing the business contract.

### 21.2 Gemini secret

`GEMINI_API_KEY` exists only in `ai-service` runtime configuration.

It must never be included in:

- browser bundles;
- Go responses;
- MongoDB records;
- AIGenerationBatch;
- AISuggestion;
- application logs;
- error responses.

## 22. Error Model

Python exposes stable machine-readable internal error classes such as:

```text
INVALID_AI_REQUEST
PROVIDER_UNAVAILABLE
PROVIDER_RATE_LIMITED
PROVIDER_TIMEOUT
INVALID_PROVIDER_RESPONSE
AI_SERVICE_UNAVAILABLE
```

Python never leaks raw provider exceptions to contractors.

Go maps internal failures into the existing public Huma problem-details model.

Example user-facing state:

```text
AI suggestions are temporarily unavailable.
Your existing project data has not been changed.

[Try Again]
```

### 22.1 Retry policy

Python may perform a small bounded retry for temporary upstream failures such as rate limiting, transient provider 5xx, or transport interruption.

There is no unbounded retry loop.

If generation ultimately fails, the batch becomes failed and no authoritative project state changes.

## 40. Key Design Decisions Locked by This Spec

1. AI runs in a Python FastAPI service; Go remains authoritative.
2. Browser never calls Python directly.
3. Gemini is the development provider behind a provider-neutral Python interface.
4. MockProvider is mandatory for deterministic automated testing.
5. Contractor enters a whole-project brief before AI-assisted Space generation.
6. Space review must happen before WorkItem generation.
7. Work Items may be Space-scoped or project-level/unassigned.
8. Missing-scope detection is included in the first WorkItem generation pass.
9. Resource generation runs as a project-level batch after confirmed WorkItems.
10. AI may suggest Materials, Trades and Equipment only in this preview.
11. AI never silently creates authoritative domain data.
12. Acceptance immediately creates/links real domain data through Go services.
13. Existing Materials can be linked; unmatched Materials use contractor-controlled Create & Add.
14. AI never selects authoritative labour rates or worker assignments.
15. `WorkResourceRequirement` is a real planning-domain entity, not AI-only storage.
16. AI suggestions stay separate from authoritative data until approval.
17. Generation batches track provider/model/prompt/schema/input provenance.
18. Hidden model reasoning is not stored.
19. Generation is synchronous for M8.5B-A.
20. Generation persistence is all-or-nothing; bulk review may have per-item partial success.
21. Generation and acceptance are idempotent.
22. Acceptance revalidates current project state and rejects stale unsafe suggestions.
23. Go validates every Space/WorkItem/Material reference returned by Python.
24. Gemini secrets remain inside the Python service.
25. UI is included in the same vertical-slice implementation run.
26. Deterministic full E2E uses MockProvider; real Gemini is a separate synthetic smoke/evaluation gate.
27. AI approval cannot directly change CostItems, Estimate totals, Quotations, RFQs, Awards, or other financial/commercial truth.

## 41. Source Alignment

This design is intentionally aligned with the approved Phase 1 product principles and extends them only where explicitly agreed during M8.5B-A design review:

- AI suggestions remain non-authoritative until contractor review.
- Scope generation supports accept/edit/reject.
- Resource assistance suggests Materials, Trades and Equipment.
- Deterministic application logic owns quantities, costs and financial totals.
- AI operates through backend-mediated authorized project context.
- Provider abstraction is preserved.
- Model/provider version tracking, prompt versioning and evaluation are governance requirements.
- Space -> Work -> Resource -> Cost -> Revenue remains the core long-term domain relationship.

The two deliberate refinements are:

1. **AI Space suggestions are added before WorkItem generation** to improve project onboarding from a whole-project brief.
2. **`WorkResourceRequirement` is added as the lightweight Work -> Resource planning bridge** so approved AI resource suggestions become real domain data without prematurely creating CostItems or procurement demand.

Both refinements preserve the Phase 1 human-review and deterministic-authority principles.

In particular, the implementation planner must verify:

- current OpenAPI generation command and generated client conventions;
- whether any existing `internal/platform/ai` abstraction should be adapted or replaced rather than duplicated.

The implementation plan must preserve existing patterns where they satisfy this design and introduce only the smallest new boundaries required for the approved feature.
