## 0. RoomPlan Migration Amendment (authoritative)

**Amendment date:** 2026-09-03. This section is the authoritative summary of the
capture-architecture change. Where any statement elsewhere in this document
conflicts with this section on the question of *which capture pipeline is the
current production path*, this section governs. Sections §8.4 through §8.4.8
remain in the document unmodified as the frozen design record of the
Kotlin/ARCore experimental provider; they are historical/reference, not
current production architecture.

### 0.1 Decision

The primary production spatial-capture architecture is now:

```text
PHYSICAL ROOM
    ↓
LiDAR / ARKit (iOS)
    ↓
Apple RoomPlan
    ↓
CapturedRoomData + CapturedRoom
    ↓
Renovex RoomPlanCaptureAdapter
    ↓
Renovex RoomDraft
    ↓
contractor spatial review / correction
    ↓
persisted scan / revisions (SpatialCaptureRun)
    ↓
confirmed immutable SpatialRoomVersion
```

The Kotlin/ARCore custom reconstruction pipeline described in §8.4 is
**FROZEN** as an experimental Android capture provider. It is preserved in
full (source, tests, fixtures, replay evidence, physical-device findings) and
may become a future Android fallback/provider, but it is no longer the
current production capture path and no further reconstruction work
(connected-wall tracing, shell simplification, Raw Depth integration,
measurement stabilization, scanner HUD refinement) proceeds on it. See §8.5
for the full freeze declaration.

### 0.2 What stays true

Every invariant in this document that concerns geometry authority,
versioning, contractor review, or downstream architecture continues to apply
unchanged, because the authority chain was always:

```text
capture-provider estimate
→ contractor review
→ server confirmation
→ immutable SpatialRoomVersion
```

RoomPlan slots into the "capture-provider estimate" role exactly where ARCore
reconstruction previously sat. `CapturedRoom` is an automatic spatial
estimate; it is not Renovex authoritative business truth, exactly as ARCore
plane/shell proposals were never authoritative.

The capture architecture change is defined primarily in §1 and §8 (§8.5–§8.29
specifically). Downstream provider-specific references throughout §§2–44 are
correspondingly generalized from Android/ARCore to iOS/RoomPlan or to
provider-neutral terminology — for example, §2.1's authority-model diagram,

previously approved authority, versioning, rendering, collaboration, or
operational architecture** — they replace an Android/ARCore-specific noun

## 1. Product Goal

M8.5C delivers a complete room-level Spatial Intelligence workflow:

```text
Physical room
→ iOS RoomPlan-assisted capture (primary; see §0, §8.6)
→ contractor-confirmed spatial truth
→ 2D plan + structural 3D
→ optional MapAnything refinement
→ AI renovation concepts
→ deterministic transformed scene
→ Web 3D + AR visualization
→ real-time collaborative editing
→ immutable concept revisions
→ reviewed operational handoff
```

The Kotlin/ARCore capture pipeline (§8.4) that previously occupied the
"AR-assisted capture" step is FROZEN per §0/§8.5 and is preserved as a
possible future Android fallback provider, not the current path.

The milestone is intentionally complete vertically but narrow horizontally: one existing Renovex `Space` / room at a time.

The primary product outcome remains the renovation end-state preview:

```text
CURRENT physical room
→ contractor-confirmed spatial truth
→ client renovation brief
→ AI design proposal
→ Go-validated concept transformation
→ interactive Concept A/B/C
→ Web 3D + iOS AR preview of the proposed finished renovation
```

Reconstruction and semantic understanding exist to improve the quality and grounding of that experience. They are supporting capabilities, not the product authority and not a prerequisite for concept generation.


```text

```

```text

→ proposes design operations

→ constraint validation
→ asset/material resolution
```

### 2.3 Visual artifacts

### 2.5 MapAnything boundary

MapAnything is a visual-refinement provider only. It never becomes authoritative for room dimensions, physical geometry, quantities, or structural truth.

## 4. Capture and Room Versioning

One `SpatialCapture` represents one scanning attempt for one existing Renovex `Space`.

A Space may have multiple captures and multiple room versions.

```text
Project
└── Space
     ├── Capture 1 → RoomVersion v1
     ├── Capture 2 → RoomVersion v2
     └── Capture 3 → RoomVersion v3 ← CURRENT
```

Confirmed room versions are immutable. A rescan creates a new room version rather than overwriting historical geometry.

### 4.1 Capture lifecycle

```text
draft
→ capturing
→ uploading
→ uploaded
→ review
→ confirmed
→ superseded
```

Failure/retry branches are allowed during capture and upload.

Important semantics:

```text
uploaded != trusted geometry
review != authoritative geometry
confirmed = contractor-approved geometry accepted by the server
```

### 4.2 Current room invariant

One Space may have at most one current confirmed `SpatialRoomVersion`.

Confirmation must be an atomic or strongly CAS-protected transition that:

1. validates the reviewed capture;
2. creates the immutable new RoomVersion;
3. supersedes the previous current RoomVersion;
4. updates `SpatialSpaceState.CurrentRoomVersionID`;
5. derives authoritative spatial quantities.

Prefer a Mongo transaction if the existing repository/deployment setup supports replica-set transactions cleanly.

## 5. Authoritative Geometry Model

V1 authoritative room geometry supports:

- arbitrary straight-edged 2D footprint;
- non-90-degree walls;
- vertical planar walls;
- one flat floor;
- one flat ceiling.

V1 first-class geometry includes:

- walls;
- openings;
- columns;
- fixed obstacles;
- plumbing points;
- electrical points;
- drain points.

### 5.1 Wall structural state

```text
unknown
non_structural
structural
```

Default: `unknown`.

AI/vision must never infer `non_structural` authoritatively from appearance alone.

### 5.2 Wall model

```text
Wall
- ID
- Start
- End
- Height
- Thickness?
- StructuralState
```

Walls use stable IDs because openings, observations, AI operations, constraints, and rebase mappings reference them.

```text
Client brief:
"Change the kitchen entrance into an arch."

→ Qwen emits modify_opening
→ Go validates geometry + wall safety

→ deterministic arched opening geometry
```

### 6.5 Architectural scope deliberately deferred

Not V1:

- curved walls;
- sloped/vaulted ceilings;
- split-level floors;
- arbitrary spline/free-form openings;
- unrestricted mesh/CAD editing.

Parametric arches do not violate the planar-wall model because the wall remains planar; only the opening profile is curved.

### 8.4 Scan Reconstruction Architecture

ARCore plane detection is observation evidence, not authoritative room
geometry. Scan Mode must reconstruct a coherent architectural proposal from
plane updates over time before it offers geometry to the contractor.

The Android reconstruction pipeline is:

```text
ARCore vertical-plane updates
→ canonical PlaneObservation
→ WallObservation
→ stateful WallCandidateTracker
→ stabilized supporting wall lines
→ plausible supporting-line intersections
→ RoomShellBuilder
→ ordered RoomShell proposal
→ existing RoomDraft
→ contractor correction and review
→ local confirmation
→ server-confirmed SpatialRoomVersion
```

The prior shortcut is prohibited:

```text
ARCore Plane
→ longest polygon diagonal
→ architectural wall
```

#### 8.4.1 Canonical plane observations

Before downstream processing, Scan Mode resolves each ARCore `Plane` through
its `subsumedBy` relationship to the topmost active plane. A subsumed child,
its replacement, and their parent must not remain as independent permanent
wall evidence.

`PlaneObservation` is session-local input evidence and contains at least:

```text
PlaneObservation
- PlaneID
- CanonicalPlaneID
- CenterXZ
- WorldNormalXZ
- WorldPolygonPoints
- UnitDirectionXZ
- SupportingLineOffset
- ObservedStartProjection
- ObservedEndProjection
- Timestamp
- TrackingState
```

ARCore does not expose a durable application ID for a plane. Android therefore
maintains a session-local registry keyed using ARCore `Plane` equality and
assigns its own opaque IDs. When a child is subsumed, its active identity is
remapped to the canonical parent. Historical diagnostic records may be kept,
but downstream active evidence must count the canonical plane once.

The ARCore source adapter transforms the local plane polygon into world-space
points. `PlaneObservationExtractor` derives the horizontal wall direction from
the plane's world-space normal. It normalizes the XZ projection of the normal,
chooses a deterministic sign so equivalent/reversed normals share one line
representation, and derives the wall direction perpendicular to that normal.
It projects every world polygon point onto the derived wall direction and uses
the minimum and maximum projections only as the currently observed extent. It
must not derive wall angle from a polygon diagonal. A degenerate
near-horizontal normal or invalid/zero-length polygon is rejected as unusable
wall evidence.

#### 8.4.2 Wall observations and candidates

One ARCore plane never means one final wall. The mapping is:

```text
ARCore plane update
→ PlaneObservation
→ WallObservation
```

`WallObservation` is ephemeral evidence containing at least:

```text
WallObservation
- CanonicalPlaneID
- UnitDirectionXZ
- UnitNormalXZ
- SupportingLineOffset
- ObservedStartProjection
- ObservedEndProjection
- Timestamp
- TrackingState
```

`WallCandidateTracker` owns the stateful architectural hypotheses used by the
mini-map. A candidate contains a stable session-local ID, smoothed direction
and supporting-line offset, accumulated observed interval union and outer
extent, observation/history statistics, last-seen time,
stability/confidence, and lifecycle state. Disconnected evidence intervals on
one supporting wall (for example either side of a doorway) remain distinct for
coverage even though they belong to one wall candidate.

Candidate matching must consider all of:

- angular similarity modulo 180 degrees;
- distance between supporting infinite lines;
- observed-extent overlap or a bounded gap, including legitimate gaps such as
  door openings;
- temporal/history consistency, so repeated convergence is stronger evidence
  than a single coincidental match.

Thresholds belong to an explicit reconstruction configuration and must be
exposed in diagnostic output. They are tuned against deterministic replay
fixtures and real-device captures rather than hidden across UI code. Numeric
angle, offset, gap, stabilization, confidence, and scoring values are tunable
scanner-policy defaults, never architectural truths. Reconstruction components
receive these parameters explicitly, and tests exercise behavior immediately
below, at, and above supplied configuration values rather than treating one
default number as universally correct.

The tracker aligns equivalent/reversed normals before averaging. Direction is
updated using normalized vector/circular averaging, and supporting-line offset
is updated with a weighted smoothed estimate. A new observation may expand the
candidate's accumulated observed interval union and outer extent immediately.
A temporarily shorter observation must not aggressively shrink either, and
loss of tracking must not make an established wall jump or disappear. Very
small observations may contribute to an already compatible candidate but must
not independently create a stable architectural wall.

#### 8.4.3 Observed extent versus architectural extent

Observed extent and architectural extent are distinct:

```text
Observed extent
= the portion of the supporting wall line currently evidenced by ARCore

Architectural extent
= endpoints inferred from plausible intersections with neighboring stable
   supporting wall lines and later accepted or corrected by the contractor
```

Raw plane polygon endpoints must never be presented as known physical room
corners. Until neighboring intersections are available, a candidate remains an
observed/stabilized segment without invented architectural endpoints.

#### 8.4.4 Wall intersections and room shell

`WallIntersectionResolver` proposes a corner only when two stable supporting
lines are non-parallel and their intersection is plausible relative to their
observed extents, stability, adjacency, and scan history. It may give a soft
confidence boost to already-near-perpendicular walls, but it must never force
90-degree angles or impose a Manhattan/rectangular room model. Arbitrary
straight-edged and angled rooms remain first-class V1 geometry.

`RoomShellBuilder` consumes stable wall candidates, plausible intersections,
and optional camera trajectory evidence. It searches for a coherent ordered,
non-self-intersecting boundary whose walls and corners explain the accumulated
observations. The camera trajectory is supporting evidence only: a shell that
cuts repeatedly through the user's path is less plausible, but a camera point
outside the proposed shell is not an absolute rejection because the user may
stand in a doorway or outside the room temporarily.

An incomplete scan must remain explicitly incomplete. The builder must not
fabricate a closing wall merely to return a polygon. A closed `RoomShell`
contains ordered stable wall references, inferred corners, observed coverage
per wall, overall confidence, and enough provenance to explain which
candidates produced each edge.

`coherent shell` does not mean `closed rectangle`. The builder may infer an
architectural corner only from supported stable-line intersections. It must not
invent a missing wall, coerce an irregular/angled cycle into a rectangle, or
mark an inferred architectural extension/gap as observed simply to make the
polygon or coverage display look clean. Shell geometry and observed-coverage
evidence remain separate outputs.

#### 8.4.5 Shell-derived product behavior

The Scan Mode state progression is:

```text
observed
→ candidate
→ stable
→ proposed shell
→ contractor confirmed
```

The mini-map distinguishes these states rather than drawing every raw plane as
an equally authoritative wall. Raw observations may be shown only as thin,
translucent developing evidence or in a developer overlay; stable candidates
are solid proposed walls; a proposed shell uses stronger edges and explicit
corner nodes; confirmed geometry is shown only after contractor review.

`Walls mapped` counts stable shell/candidate walls, never raw ARCore planes or
frame observations. Once a shell exists, coverage is the length-weighted
amount of that likely shell with sufficient observation confidence. Before a
shell exists, coverage may use documented angular-sector plus stable-candidate
evidence, but it must remain explicitly provisional. Directional guidance
uses missing/weak shell evidence, candidate confidence, camera pose, and
camera orientation to distinguish prompts such as scanning a remaining wall,
moving toward a corner, or moving sideways to improve a wall.

The generated closed shell feeds the existing `RoomDraft` model. Proposed
corners and walls receive stable draft IDs at proposal creation; subsequent
contractor edits use the existing correction operations. Automatic geometry
remains a proposal. Contractor correction wins, local confirmation remains
non-authoritative, and only server confirmation creates a trusted immutable
`SpatialRoomVersion`.

#### 8.4.6 Diagnostics and deterministic evidence

Threshold tuning requires stage-level instrumentation. A developer/debug view
must expose at least:

```text
raw vertical planes
canonical planes
wall observations
wall candidates
stable walls
room-shell state and confidence
```

Per-candidate diagnostics include observation count, direction/normal
variance, supporting-line offset variance, observed extent, last-seen time,
and stability. Deterministic replay fixtures cover at least a simple
rectangular room, fragmented single wall, slightly rotated observations,
offset observations, plane subsumption, partial scan, L-shaped room, angled
wall room, noisy corner, revisited wall, open doorway, and incomplete shell.

Assertions must target architectural outcomes, for example:

```text
multiple noisy plane observations
→ four stable wall candidates
→ four plausible intersections
→ one coherent ordered room shell
```

rather than preserving a raw segment-count or cluster-count implementation.

#### 8.4.7 Task 5 closure: trace evaluation, proposal freeze, and review authority

Before adding further shell cleanup rules, Android must evaluate a
deterministic connected `WallTraceBuilder` over the existing stable
`WallCandidate` evidence. The evaluation asks which supported adjacent wall
continues an architectural boundary. It does not replace global evidence
collection and must not assume rectangles, Manhattan geometry, right angles,
or a minimum architectural wall length. It must preserve angled rooms,
L-shaped rooms, genuine short returns, doorway gaps, and revisited walls.

`WallTraceBuilder` is adopted only if a deterministic comparison against
`RoomShellBuilder` proves it preserves every valid replay outcome while
materially reducing redundant wall selection, object-sized loops, and
micro-chamfers. Otherwise `RoomShellBuilder` remains authoritative. The
comparison distinguishes raw ARCore replay fixtures from reconstructed
stable-candidate/shell regression fixtures. In particular, the recorded
Xiaomi 11T nine-edge case is explicitly reconstructed evidence: it preserves
the observed architectural failure mode but does not claim to reproduce the
original frame-by-frame ARCore history.

If micro-chamfers remain, simplification is permitted only at the
`RoomShell` to `RoomDraft` architectural boundary. Edge length alone is never
sufficient. A collapse requires supporting-line/provenance evidence, a
coherent replacement intersection, displacement within configured tolerance,
no self-intersection, and preserved room topology. Original observations and
supporting-line provenance remain available. All numeric tolerances are
scanner parameters and receive below/at/above boundary tests.

Acquisition has an explicit lifecycle:

```text
SCANNING
-> READY_TO_REVIEW
-> REVIEWING
-> LOCALLY_CONFIRMED
```

A closed polygon alone cannot produce `READY_TO_REVIEW`. Readiness combines
configured boundary plausibility, topology validity, coverage/evidence
sufficiency, proposal stability over time, and relevant tracking/evidence
quality. Reaching readiness latches a strictly immutable
`RoomProposalSnapshot`: the exact scanner proposal displayed to the user.
Review never mutates this baseline.

Contractor editing uses a separate `RoomDraftWorkingCopy`. `Apply` commits the
working copy into the current applied `RoomDraft`; `Cancel` discards the
unapplied operation; `Reset` reconstructs `RoomDraft` from the immutable
`RoomProposalSnapshot`; and `Confirm room` locally confirms the current
applied `RoomDraft`. Local confirmation remains in-process Task 5 state and
does not create a backend `SpatialRoomVersion`. `Continue scanning` discards
the current review working copy, resumes acquisition from scanner state, and
allows a new immutable proposal snapshot to evolve.

The review editor exposes a clean 2D boundary with clear selection state and
real Apply/Cancel/Reset semantics. Editable source geometry comprises corners,
openings, ceiling height, and exposed obstacle/service-point properties.
Derived wall lengths, perimeter, floor area, wall areas, opening areas, and
net wall areas recompute deterministically and never become independent
editable scalars. Every affordance that looks interactive must perform a real
supported edit; unsupported operations must not be presented as buttons,
chevrons, clickable rows, or other interactive controls.

Ceiling height is evidence-qualified. A stable floor/ceiling evidence pipeline
may produce a detected proposal later, but the current vertical-plane
reconstruction must not fabricate certainty. Without reliable evidence the
height is `UNCONFIRMED` and wall-area quantities remain unavailable until the
contractor enters a measurement. A contractor-entered value is
`CONTRACTOR_CORRECTED`. The current hard-coded 2.40 m default is not a detected
measurement and must not be shown as one.

Task 5 local measurements use frozen or edited architectural geometry: wall
length is corner-to-corner distance, perimeter is the sum of wall lengths,
and floor area is the ordered-polygon shoelace area. When height is available,
gross wall area is wall length times height. Rectangle opening area is width
times height; arch area is its rectangular spring section plus the
semi-elliptical cap defined by width and arch rise. Net wall area subtracts
opening areas. These remain proposal/review quantities; the backend later
recomputes authoritative quantities from confirmed spatial truth.

Pending proposal continuity is process-local in Task 5. Returning to a space
with a valid pending proposal offers `Continue Review`; durable restart/offline
persistence remains Task 6.

#### 8.4.8 Explicit non-goals

This refinement uses the ARCore information already available. It must not
expand into:

- custom SLAM;
- custom computer-vision wall segmentation;
- neural room-layout inference;
- full depth point-cloud reconstruction;
- Manhattan-world or rectangle enforcement.

Depth remains supplementary and deferred until the corrected plane →
observation → candidate → shell pipeline has been validated. It may later
improve acquisition speed, wall distance, difficult-plane evidence, or corner
confidence, but it does not replace contractor review or the supporting-line
architecture.

### 8.6.2 Critical authority rule

`CapturedRoom` is an automatic spatial estimate. It is **not** Renovex
authoritative business truth. This is the same authority rule that already

```text
RoomPlan
→ RoomDraft
→ contractor review
→ confirmed SpatialRoomVersion
```

## 8.7 Capture Provider Integration Boundary

Introduce a provider-neutral abstraction, not a RoomPlan-specific one, so a
future capture source (including a revived Android/ARCore fallback, §8.5)
can implement the same contract without conforming to something named after
Apple's framework:

```text
SpatialCaptureProvider              (protocol/interface, provider-neutral)
    ├── RoomPlanCaptureProvider     (current — iOS, Apple RoomPlan)
    └── AndroidCaptureProvider      (future, if the frozen provider is ever revived — not implemented now)

RoomPlanCaptureAdapter              (Apple-specific, RoomPlan-only)
```

`SpatialCaptureProvider` is the platform-neutral contract: obtain a capture
result and hand it off for normalization. `RoomPlanCaptureProvider` is its
concrete iOS/RoomPlan implementation — it obtains a RoomPlan capture result
(via `RoomCaptureView` or, later, `RoomCaptureSession`). `RoomPlanCaptureAdapter`
is Apple-specific by design: it is the one place that knows about
`CapturedRoom`/`CapturedRoomData` and converts that Apple-specific spatial
output into the canonical Renovex `RoomDraft`.

```text
capture provider (SpatialCaptureProvider conformer)
      ↓
provider-specific adapter (e.g. RoomPlanCaptureAdapter)
      ↓
canonical RoomDraft
```

Apple framework types (`CapturedRoom`, `CapturedRoom.Wall`, `simd_float4x4`,
etc.) must not leak into:

- the backend;
- Web;
- shared domain contracts;
- business logic.

Everything downstream of the adapter consumes Renovex spatial contracts only.
`SpatialCaptureProvider` itself must not carry any Apple-specific types in
its signature — only `RoomPlanCaptureProvider`'s implementation and
`RoomPlanCaptureAdapter` may reference RoomPlan/ARKit types.

### 8.7.1 Capture UX transition plan

The design must not couple the app permanently to `RoomCaptureView`.

Initial implementation (RP1/RP2, see §33 amendment in the implementation
plan):

```text
RoomCaptureView
→ use Apple's provided capture UX as much as possible
```

Future production/custom capture:

```text
RoomCaptureSession
+ Apple's RoomPlan guidance
+ Renovex Live Capture tools (§8.17)
```

The `RoomPlanCaptureProvider` implementation must support this future
transition (from the built-in view to a custom session-driven overlay)
without a domain redesign — the adapter boundary and `RoomDraft` contract do
not change when the capture UI changes.

## 8.8 Canonical Renovex Coordinate System

Define one canonical Renovex room-local coordinate frame, established at the
`RoomPlanCaptureAdapter` boundary:

- **units:** metres;
- **origin:** the room-local origin is adapter-defined at normalization time
  (e.g. first confirmed floor-plane point or room bounding-box corner — exact
  convention fixed during implementation, not per-capture ad hoc);
- **axes:** right-handed, Y-up, matching the existing Renovex `SceneManifest`
  convention already used for structural 2D/3D (§14) and AI scene rendering
  (§25) so no second coordinate convention is introduced;
- **handedness:** right-handed;
- **matrix convention:** column-major 4x4 transforms, consistent with
  `simd_float4x4` source data and Three.js/R3F consumption on Web;
- **quaternion/rotation convention:** unit quaternions, Renovex-normalized
  sign, consistent between iOS, Web, and backend geometry validation;
- **surface-local → room-local:** every RoomPlan surface/object transform is
  expressed relative to the RoomPlan session origin on input and re-expressed
  relative to the Renovex room-local origin by the adapter before it reaches
  `RoomDraft`;
- **RoomPlan → Renovex conversion:** owned exclusively by
  `RoomPlanCaptureAdapter`; no other component reinterprets RoomPlan
  coordinates.

```text
RoomPlan coordinates
        ↓
RoomPlanCaptureAdapter
        ↓
RENOVEX ROOM-LOCAL FRAME
        ↓
iOS / Web / Backend
```

No downstream component may independently reinterpret Apple's coordinate
system. This mirrors the existing rule that renderers consume the canonical
`SceneManifest` and never reinterpret AI instructions (§2.4) — the same
"single conversion point, many neutral consumers" pattern applies to spatial
coordinates.

### 8.8.1 Cross-platform contract tests

Require fixture/contract tests proving a wall, door, window, object, opening,
and measurement produce equivalent positions/orientations in:

- iOS domain (post-adapter `RoomDraft`);
- Web renderer (`SceneManifest` consumption);
- backend geometry (validation/quantity derivation).

These tests extend the existing Cross-Renderer Contract Tests requirement
(§30 of the implementation plan) rather than introducing a parallel test
concept.

## 8.9 Stable Renovex Domain Identities

RoomPlan identifiers (`CapturedRoom.Wall.identifier`, etc.) are capture-source
provenance only. They must **not** be treated as permanent Renovex domain
identity, for the same reason ARCore plane IDs were never treated as durable
architectural IDs (§8.4.1 of the frozen provider design).

Every normalized element receives a Renovex-owned stable ID:

- `WallID`
- `OpeningID`
- door/window representation ID where applicable
- `ObjectID`
- `FixtureID`
- `ConstraintID`
- `ServicePointID`

Preserve source provenance on each element:

```text
sourceProvider = roomplan
sourceRoomPlanIdentifier = ...
```

A rescan may produce entirely different RoomPlan source identifiers for what
is physically the same wall. Rebase/matching between scans (§28) must
eventually use geometry, spatial relationships, semantics, and provenance —
never equality of RoomPlan source identifiers alone. This is consistent with
the existing rebase design, which already keys correspondence on geometric/
semantic matching rather than raw identifier equality.

## 8.10 Live RoomPlan Update Identity / No Duplicate Rendering

This explicitly prevents the duplicate-wall accumulation problem experienced
in the frozen Kotlin/ARCore scanner (the reason §8.4 required canonical plane
subsumption in the first place, §8.4.1).

During one RoomPlan capture session, maintain current-state maps keyed by
RoomPlan identifiers:

```text
didAdd
→ create/update live representation

didChange / didUpdate
→ replace/refine the current representation
→ MUST NOT append duplicate render geometry for the same identifier

didRemove
→ remove the current representation
```

Do not accumulate every historical RoomPlan callback as an independent wall,
opening, or object. After RoomPlan processing completes:

```text
CapturedRoom
→ adapter
→ stable Renovex IDs
```

Include only a bounded, deterministic topology sanity pass for obviously
coincident/redundant surfaces at the adapter boundary.

Do **not** recreate a custom `RoomShell` reconstruction system — that
architecture is frozen with the ARCore provider (§8.5) and is not reused for
RoomPlan, which already performs its own session-level surface reconciliation.

Do **not** aggressively merge nearby walls solely by distance; genuine
parallel structural surfaces may exist, exactly as the frozen design already
warned against distance-only merging (§8.4.7's simplifier required
provenance, not edge length alone).

## 8.15 Doors, Windows, and Openings

RoomPlan provides initial detection, but Renovex must support contractor
correction because RoomPlan may:

- classify a door as a generic opening;
- merge/split unusual door configurations;
- fail on double doors;
- omit door swing;
- incorrectly represent partially open double doors;
- simplify complex windows;
- imperfectly represent opening geometry.

- add opening;
- remove opening;
- resize;
- reposition along parent wall;
- merge/split where supported;
- opening ↔ single door ↔ double door ↔ window reclassification.

authoritative backend contract; RoomPlan is simply a new upstream evidence
source feeding that same contract via the adapter and contractor review.

## 8.18 Measurement Authority and Provenance

RoomPlan dimensions are estimates, not absolute surveying truth. Formalize
measurement evidence with at least:

```text
ROOMPLAN_ESTIMATED
AR_VERIFIED
PHYSICAL_VERIFIED
```

Allow future `LASER_VERIFIED`.

Conceptually:

```text
MeasurementEvidence
- ID
- element ID
- quantity/type
- value
- unit
- method
- captured/measured by
- measured at
- confidence/status
- source metadata
- superseded/current relationship where applicable
```

Preserve evidence history rather than silently overwriting it. Example:


for spatial quantities in §15 and for the frozen Android provider's
`RoomDraftMeasurements` (§8.4.7). `MeasurementEvidence` sits alongside, and
feeds, the existing §15 Authoritative Spatial Quantities provenance model
rather than replacing it: §15 remains the backend-authoritative quantity
derivation from confirmed geometry; `MeasurementEvidence` is the pre-
confirmation evidence trail that justifies which geometry gets confirmed.

## 8.22 Multiple Capture Runs and Persistence

This is a **hard requirement** and directly fixes the previous Android
one-off capture behavior (the frozen provider's Task 6 durable-persistence
work, which had not been reached before this amendment — see §33 reordering
in the implementation plan).

Every usable RoomPlan scan becomes a persisted capture-run record
(provisionally named `SpatialCaptureRun` in this document; see the storage-
shape note below). One Renovex `Space` may have multiple capture runs:

```text
Living Room
├── Scan #1
├── Scan #2
├── Scan #3
└── Current confirmed RoomVersion
```

A new scan must **not** overwrite an old scan — this generalizes the existing
§4 Capture and Room Versioning model (multiple captures, multiple immutable
RoomVersions per Space, current-room invariant) to explicit multi-run
persistence at the capture-run level, one layer beneath `SpatialRoomVersion`.

Conceptually:

```text
SpatialCaptureRun
- ID
- CompanyID
- ProjectID
- SpaceID
- capture number
- provider = roomplan
- status
- captured at/by
- device metadata
- raw CapturedRoomData artifact
- processed RoomPlan artifact
- RoomDraft association
- optional USDZ
- optional curated keyframes
- sync status
- created/updated timestamps
```

Persist immediately after usable RoomPlan processing. Required ordering:

```text
RoomPlan completion
→ persist source/raw result
→ normalize RoomDraft
→ persist RoomDraft
→ THEN present normal Room Review
```

Do not allow capture → in-memory only → navigation → data lost.

This section introduces the **capture-run persistence concept** required to
preserve every physical scanning attempt: one record per usable RoomPlan
scan, holding raw/processed provider artifacts and a `RoomDraft` association,
so that no scan is ever silently lost or overwritten. `SpatialCaptureRun` is
the name used in this document for that concept, sitting conceptually
alongside the existing `SpatialCapture` lifecycle model in §4.1
(`draft → capturing → uploading → uploaded → review → confirmed →
superseded`).

During Task 1 repository inspection (implementation plan), map this concept
onto the existing persistence model as either an extension of the existing
`SpatialCapture` record or a distinct `SpatialCaptureRun` record referenced
by it — whichever fits the inspected repository more cleanly. **The
behavioral guarantees above are fixed (multi-run, no overwrite, persist
before Room Review, immediate persistence after processing); the storage
shape is not.** Do not create a new Mongo collection or record type merely
because this document uses the name `SpatialCaptureRun` — that name may end
up being an extended `SpatialCapture`, not a new collection.

## 10. Offline Mobile Behavior

Capture is offline resilient.

Without connectivity the mobile capture client (currently the iOS RoomPlan
client; the frozen Android/ARCore client historically satisfied this
identically) may continue room scanning, geometry review, opening
correction, obstacle/service marking, observations, photos, and local
confirmation.

Unsynced capture state must survive application restart, phone restart, backgrounding, and temporary connectivity loss.

### 10.1 Local authority

Offline confirmation means:

```text
locally_confirmed
```

It does not create authoritative server state.

When connectivity returns:

```text
upload artifacts
→ finalize upload manifest
→ server re-authorizes tenant/project/space/capability
→ server validates artifacts + geometry
→ confirm command
→ SpatialRoomVersion created
```

### 10.2 Resumable uploads

Uploads resume artifact-by-artifact. Unsynced capture artifacts must not be automatically deleted.

### 10.3 Online-only capabilities

Network is required for authoritative server confirmation, MapAnything, Qwen concept generation, external asset resolution/import, persistent AR localization host/resolve (§13), and real-time collaboration.

Cached concepts may be viewed offline if required assets are already available. Shared draft editing becomes read-only offline. No V1 offline collaborative merge.

**RoomPlan amendment note:** This section's original design used ARCore
Cloud Anchors, the natural choice for the frozen Android/ARCore client. With
iOS as the production AR client, the model below is now **provider-neutral**:
it names a generic persistent-localization layer rather than presupposing
Cloud Anchors. **Do not silently assume the Android Cloud Anchor
implementation transfers unchanged.** Task 1 repository inspection
(implementation plan) explicitly selects the concrete iOS localization
mechanism and SDK before this section's `Provider` field and manual-alignment
fallback are implemented for RoomPlan capture — candidates include ARKit's
`ARWorldMap` (Apple's own mechanism for saving a mapped environment and
resuming/relocalizing a persistent AR experience after relaunch — the most
natural fit for room-level persistent localization) or a cross-platform Cloud
Anchor SDK if one is adopted for multi-device/shared-AR scenarios. Apple's
`ARGeoAnchor` is a geographic latitude/longitude/altitude anchor and is not a
fit for indoor room-level localization; it is not a candidate here. Task 1
makes the final decision; this section's job is to define the
provider-neutral contract that decision plugs into.

A persistent AR localization layer sits separately from room geometry.

```text
RoomARLocalization
- ID
- CompanyID
- RoomVersionID
- Provider
- ProviderLocalizationID?
- LocalizationArtifactID?
- RoomToLocalizationTransform
- Status
- HostedAt
- ExpiresAt?
```

`Provider` records which concrete mechanism was used (e.g. `arworldmap`,
`cloud_anchor`, or a future value) — the record shape itself does not
presuppose any one of them. `ProviderLocalizationID` and
`LocalizationArtifactID` are optional because different providers represent
their persisted localization state differently (an opaque hosted anchor ID
for a Cloud Anchor–style provider; a stored world-map artifact reference for
an `ARWorldMap`–style provider).

Meaning:

```text
Room-local coordinates
= where Renovex content exists

Persistent AR localization
= how AR finds the physical room coordinate frame again
```

Persistent AR localization failure never invalidates room geometry — it only
degrades to the manual alignment fallback below. (The frozen Android
provider's historical design specifically stated "Cloud Anchor failure never
invalidates room geometry"; the invariant is unchanged, only the mechanism
name is generalized.)

### 13.1 Manual alignment fallback

If automatic resolution fails:

```text
1. Select known wall/corner
2. Align first room point
3. Align second point along known wall
4. Confirm orientation
```

Renovex derives the transform between the current AR session and the confirmed room-local frame.

```text

        ↓
```

- refrigerators/appliances;
- dining tables;
- sofas;

- vanities;



After the golden acceptance gate passes, M8.5C freezes.

Deferred:

- property-wide multi-room registration;
- whole-property reconstruction;
- curved walls;
- sloped/vaulted ceilings;
- split levels;
- BIM/IFC;
- automatic defect diagnosis;
- comprehensive automatic takeoff;
- massive asset marketplace;
- supplier-product 3D mapping;
- unrestricted CAD;
- full offline collaboration/conflict merge;
- photorealistic production rendering;
- general Project Copilot orchestration;
- making a specific third-party semantic parser model mandatory for production;
- automatic parser-driven mutation of confirmed room geometry;
- RoomPlan `CapturedStructure` whole-property multi-room registration (§8.26);
- reviving the frozen Kotlin/ARCore capture provider (§8.5) as an active Android fallback, without a separate explicit unfreeze decision;
- a full custom `RoomCaptureSession`-based scanning HUD beyond the scoped Measure/Mark/Note boundary (§8.17).

Roadmap:

```text
M8.5C Spatial Intelligence
→ FREEZE
```

## 46. Final Architectural Invariants

1. AR estimates never become authoritative without contractor review and server confirmation.
2. One Space has at most one current confirmed RoomVersion.
3. Confirmed RoomVersion geometry is immutable.
4. Historical RoomVersions remain preserved.
5. Observations bind to exact RoomVersions.
6. Concept revisions bind to exact RoomVersions.
7. Concept revisions are immutable.
8. Working-draft mutations use revision/CAS.
9. Rebase creates new state; it never rewrites history.
10. Renderers consume canonical SceneManifest.
11. Large spatial artifacts stay outside Mongo.
12. MapAnything never establishes authoritative geometry/scale.
13. AI output never writes domain state directly.
14. Go owns safety and validation.
15. Sensitive changes require explicit verification.
16. Spatial base quantities may be authoritative; procurement/resource allowances remain suggestions until reviewed.
17. Spatial does not directly mutate commercial domains.
18. WebSocket previews are transient and do not bypass domain validation.
19. Object leases do not grant authorization.
20. Offline capture is resilient, while offline collaborative merge remains deliberately unsupported.
21. UI/UX behavior described above is part of milestone correctness.
22. `SpatialSceneParser` output is always non-authoritative and optional.
23. `ExistingSceneObject` records require explicit review/confirmation before entering the trusted existing-room semantic inventory.
24. `SpatialDiscrepancy` records are review signals and never mutate confirmed RoomVersions automatically.
25. Qwen concept generation must remain functional without semantic parsing.
26. M8.5C closes only after the complete one-room golden workflow passes end-to-end.
27. ARCore planes and polygons are observation evidence, never architectural walls or room corners. **(Applies to the FROZEN Kotlin/ARCore provider, §8.5; not exercised by the current RoomPlan path.)**
28. Subsumed ARCore planes are canonicalized before wall-candidate tracking. **(FROZEN provider, §8.5.)**
29. Observed wall extent remains distinct from intersection-derived architectural extent. **(FROZEN provider, §8.5.)**
30. RoomShell construction preserves arbitrary straight-edged geometry and never forces a Manhattan/rectangular room model. **(FROZEN provider, §8.5.)**
31. Scan Mode wall count, coverage, and guidance derive from candidate/shell state rather than raw plane updates. **(FROZEN provider, §8.5.)**
32. A generated RoomShell becomes only an editable RoomDraft proposal; contractor review and server confirmation remain the authority boundary. **(FROZEN provider, §8.5; the general principle — automatic capture output is a proposal, not authority — is restated for RoomPlan in invariant 33 below.)**
33. `CapturedRoom` is an automatic spatial estimate, never authoritative business truth; only contractor review and server confirmation produce a trusted `SpatialRoomVersion` (§8.6.2).
34. RoomPlan/ARKit identifiers are capture-source provenance only; every normalized spatial element receives a Renovex-owned stable ID, and rescans are matched by geometry/semantics/provenance, never by RoomPlan identifier equality (§8.9).
35. Live RoomPlan session updates (`didAdd`/`didChange`/`didUpdate`/`didRemove`) update one current-state representation per identifier; historical callbacks are never accumulated as independent duplicate walls/openings/objects (§8.10).
36. RoomPlan wall thickness, dimensions, and opening classification are corrigible estimates; a contractor-applied verified measurement or reclassification updates `RoomDraft` geometry (2D, 3D, and dependent quantities together), never just a displayed number (§8.14, §8.15, §8.18).
37. Every usable RoomPlan scan is persisted as a capture-run record (provisionally named `SpatialCaptureRun`; exact repository representation determined by Task 1) before Room Review is presented; a new scan never overwrites a prior scan; capture must not exist only in memory before navigation (§8.22).
38. The canonical Renovex room-local coordinate frame (§8.8) is the single conversion target for RoomPlan output; no downstream component (iOS, Web, or backend) independently reinterprets Apple's coordinate system.
39. `RoomDraft` is the single mutable contractor-review spatial model shared by iOS and Web; RoomPlan's USDZ/built-in post-scan view is never the primary editable model (§8.11, §8.21).
