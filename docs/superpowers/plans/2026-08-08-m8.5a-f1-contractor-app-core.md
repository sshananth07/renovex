# M8.5A — F1: Contractor App Core — Implementation Plan

## Status

**Architecture-approved.** Supersedes the earlier draft (session-scratch plan
`whimsical-wondering-dongarra.md`), which predated the approved
`frontend-architecture.md` / `frontend-auth-session-contract.md` documents and
used a hand-maintained-types, custom-hook, manual-walkthrough approach
inconsistent with what is now the fixed architecture.

Four non-architectural corrections were applied after approval, before
implementation began: an explicit `Providers` component boundary (§5a) with
`QueryClientProvider` outside `AuthProvider` and no global `QueryClient`
singleton; `/auth/me` and the current-user projection stay owned by
`AuthProvider` only, never duplicated into a TanStack Query cache entry
(§6); MSW plus shared isolated test-provider infrastructure added to the
test toolchain (§3, §16); the Playwright single-flight test (F1.10) made
deterministic via two synthetic-401 route intercepts rather than racing a
real token expiry, with the real `/auth/refresh` and both retries left to
hit the live backend; auth redirects use `router.replace`, not
`router.push`; responsive breakpoint behavior is proven only in Playwright
(F1.10/F1.3), not asserted via jsdom viewport mocking.

Implementation begins at F1.0 immediately following this revision.

- `docs/superpowers/specs/frontend-architecture.md` — full stack, surfaces,

This plan reconciles the earlier draft against both documents and against the
live `apps/web/openapi/openapi.json` contract, correcting every area the user

safe `returnTo`, responsive shell, Malaysia-first formatting, and automated

`POST /auth/refresh`; current user via `GET /auth/me`; client-side
`AuthProvider`/`AuthGate`; coordinated single-flight refresh on 401; no
Next.js BFF/session layer; no middleware/proxy as auth authority.

### 1.1 Contradiction check performed before writing this plan

Read in full: `phase1.md` (Property/Space sections), ADR 0001, ADR 0002,
both frontend architecture documents, `apps/web/openapi/openapi.json`
(every F1-relevant path and schema), the Next.js 16 bundled docs referenced
by `apps/web/AGENTS.md` (authentication guide, route-groups, version-16
upgrade notes, Vitest/Playwright setup guides).

**No contradiction requiring escalation was found.** Two contract nuances the
earlier draft got wrong, corrected here (not architecture conflicts — just
facts about the live OpenAPI contract that change implementation details):

1. **`GET /properties` does not use the canonical `{items,page,pageSize,total}`
   envelope.** Its response schema is `ListPropertiesOutputBody` →
   `{properties: PropertyDTO[] | null}` (0 or 1 entries per Project, per
   `phase1.md` §6 and the README). It also isn't independently paginated —
   it takes only a required `projectId` query param. `PATCH /properties/{id}`
   (`UpdatePropertyInputBody`) requires `address` on every update — it is
   *not* a genuine partial PATCH like Clients/Projects/WorkItems; only
   `notes`/`propertyType` are optional. The plan's Property feature code
   must NOT reuse the generic paginated-list/genuine-partial-PATCH patterns
   built for Clients/Spaces/WorkItems.
2. **`GET /spaces` and `GET /clients` do use the canonical envelope** and are
   genuinely paginated (`page`/`pageSize`/`search`/`sort`/`order`), matching
   the architecture doc's §17 exactly.

No Next.js 16 breaking change conflicts with the approved architecture. The
authentication guide's Server-Action/cookie/Proxy patterns are the
*rejected* alternative our fixed contract explicitly forbids — confirmed,
not adopted. `params`/`searchParams` are async-only in Next.js 16 (relevant
to the dynamic `[clientId]`/`[projectId]` route handlers — `await params`).

## 5. Layered Design (per `frontend-architecture.md` §5)

```
openapi.json
    → openapi-typescript → src/lib/api/generated/schema.ts   (transport types only)
    → openapi-fetch client (src/lib/api/client.ts)             (bearer + 401 + credentials)
    → feature api.ts (thin typed wrappers per feature)
    → TanStack Query hooks (queries.ts / mutations.ts)
    → feature components (consume query/mutation hooks, render via shared UI)
```

`client.ts` owns exactly what §6 of the architecture doc specifies: base URL,
`credentials: "include"`, bearer injection from the in-memory token holder,
single retry after coordinated refresh, request correlation, typed
transport. It does not know about React, TanStack Query, or any feature.

### 5a. Providers boundary

**Files**: `src/app/providers.tsx` (client component), `src/lib/query/
queryClient.ts` (factory, not a singleton).

```tsx
// src/lib/query/queryClient.ts
export function createQueryClient(): QueryClient {
  return new QueryClient({ /* defaults */ });
}

// src/app/providers.tsx
"use client";
export function Providers({ children }: { children: React.ReactNode }) {
  const [queryClient] = useState(createQueryClient);
  return (
    <QueryClientProvider client={queryClient}>
      <AuthProvider>{children}</AuthProvider>
    </QueryClientProvider>
  );
}
```

`QueryClientProvider` wraps `AuthProvider`, not the reverse: `AuthProvider`
needs to be able to call `queryClient.clear()` on logout/session-loss (via
`useQueryClient()`), which requires it to render *underneath* the Query
provider in the tree. `queryClient.ts` exports a **factory function**, not a
module-level singleton instance — `Providers` constructs one instance per
component-tree mount via `useState(createQueryClient)`, so each test render
and each real app mount gets its own isolated `QueryClient` with no shared
mutable state leaking between them (a singleton would let one Vitest test's
cached query data bleed into the next test, or — in the unlikely case of
SSR — leak data across requests).

`src/app/layout.tsx` (the single true root layout) renders
`<Providers>{children}</Providers>` once; neither `(auth)/layout.tsx` nor
`(app)/layout.tsx` create their own `QueryClientProvider` or `AuthProvider`.

**Single-flight refresh** (`features/auth/singleFlightRefresh.ts`): a
module-level `let inFlight: Promise<string> | null`. `ensureFreshToken()`
returns the existing promise if set, otherwise starts one POSTing
`/auth/refresh` via a *raw* fetch (not through `client.ts`, to guarantee the
refresh call itself can never recursively trigger the 401→refresh path),
stores the new token in the in-memory holder on success, clears `inFlight`
in `finally`, and on failure clears the token holder and rejects (callers —
the client's 401 handler and `AuthProvider`'s bootstrap — both react to
that rejection to enter the unauthenticated state).

## 6. Auth State Model

```ts
type AuthStatus = "initializing" | "authenticated" | "unauthenticated";
```

`AuthProvider` (client component, wraps the whole tree from the true root
`app/layout.tsx`, rendered inside `Providers`/`QueryClientProvider` per §5a,
so both `(auth)` and `(app)` route groups share one auth state):
1. On mount: `status = "initializing"`, call `ensureFreshToken()`.
2. On success: call `GET /auth/me` directly (plain async call inside
   `AuthProvider`'s own effect/state — **not** a `useQuery` hook), populate
   `user` in `AuthProvider`'s own React state, `status = "authenticated"`.
3. On failure (refresh rejected): `status = "unauthenticated"`, no redirect
   yet — `AuthGate` handles redirect for protected segments only.
4. Exposes `login(email,password)`, `register(...)`, `logout()`,
   `refetchMe()` (re-calls `GET /auth/me` and updates `user` in place).

**`/auth/me` and the current-user projection are owned exclusively by
`AuthProvider`**, never mirrored into a TanStack Query cache entry. The
current user is authentication/session state, not server-resource state —
architecture §7.2 assigns it to the auth layer, and duplicating it into
Query as well (e.g. a `useQuery(["me"], getMe)`) would create two
independently-invalidated sources of truth for the same identity data,
which is exactly the kind of hidden state the architecture doc's server-
state/auth-state split is designed to prevent. Any component needing the
current user calls `useAuth()`, never a query hook.

`AuthGate` (wraps `(app)/layout.tsx` children): renders a loading state
while `"initializing"`; renders children while `"authenticated"`; redirects
via `router.replace("/login?returnTo=<safe-path>")` (not `router.push`)
while `"unauthenticated"` — a redirect away from a route the user isn't
authorized to be on should not leave that route as a back-button target,
matching how session-loss redirects are conventionally handled and avoiding
a back-navigation loop between the gated route and `/login`.

**Logout** (`frontend-auth-session-contract.md` "Logout" + `queryClient.ts`):
`POST /auth/logout` (best-effort — clear local state even if the network
call fails per the contract), clear in-memory token, clear `user` (in
`AuthProvider`'s own state), call the `QueryClient` instance's `.clear()`
(obtained via `useQueryClient()` inside `AuthProvider`, which works because
`AuthProvider` renders under `QueryClientProvider` per §5a — removes all
authenticated TanStack Query cache so no data survives into a different
session), then `router.replace("/login")` (not `router.push`, for the same
back-navigation reasoning as `AuthGate`).

**Safe `returnTo`** (`features/auth/returnTo.ts`): a pure function
`parseSafeReturnTo(value: string | null): string` — accepts only a string
starting with a single `/` and not `//` (protocol-relative) and not
containing `://`; anything else (including `null`) falls back to
`/dashboard`. Used by the login page to redirect back after successful
auth, and by `AuthGate` when constructing the redirect URL.

## 7. Server State, URL State, Form State

- **TanStack Query** owns every authenticated *resource* read (`Clients`,
  `Projects`, `Properties`, `Spaces`, `WorkItems`). `/auth/me` and the
  current-user projection are explicitly **not** in this list — per §6,
  they belong to `AuthProvider` alone. Query keys include all server-visible
  filters, e.g.
  `["clients", {page,pageSize,search,sort,order}]`,
  `["projects", projectId, "properties"]`. Mutations invalidate only their
  own affected keys.
- **URL search params** own list page/search/sort/order state for Clients,
  Projects, Spaces, Work Items (the four canonically-paginated resources).
  `lib/url/listParams.ts` provides a small typed
  `useListSearchParams()` hook wrapping Next's `useSearchParams`/
  `useRouter` — read-only parsing + a `setParams(partial)` writer that
  merges into the URL via `router.replace` (no full navigation), always
  resetting `page` to `1` when `search`/`sort`/`order` changes. This
  replaces the earlier draft's custom `useListQuery` hook, which owned
  fetch state itself — that responsibility now belongs to TanStack Query;
  this hook owns only URL-derived filter state, matching architecture §7.3
  exactly ("Do not make page/search/sort state live only inside a custom
  React hook").
- **React Hook Form + Zod** own all create/edit forms. Each feature's
  `schemas.ts` defines a Zod schema mirroring the OpenAPI input schema's
  required/optional shape (not duplicating business validation — only
  obvious required/format checks, backend remains authoritative). RHF's
  `zodResolver` wires the two together.
- **Local component state** for dialog/drawer open-state only.

## 8. Shared List/Detail Patterns

- **`components/layout/PaginatedTable.tsx`** — presentation only: columns,
  rows, sort-header clicks (emits `onSortChange`), page controls (emits
  `onPageChange`), loading/empty/error slots. Receives already-fetched data;
  never calls an endpoint itself. Used by Clients, Projects, Spaces, Work
  Items list pages — **not** by Properties (0-or-1, no pagination).
- Each feature's `queries.ts` exposes a `useXList(params)` hook wrapping
  `useQuery` with the feature's typed `api.ts` list call; the page component
  wires `useListSearchParams()` output into that hook and passes the result
  into `PaginatedTable`.
- **Property** gets its own simple `PropertyDetail`/`PropertyForm`
  components (no `PaginatedTable`, no list-URL-params) reflecting its
  distinct, non-paginated, 0-or-1, non-tri-state-PATCH contract.

## 9. Progressive Project Setup (architecture §14)

The Project Overview page (`(app)/projects/[projectId]/page.tsx`) derives
setup progress purely from authoritative backend reads — no duplicate
frontend workflow state:

```ts
// features/projects/setupProgress.ts
type SetupProgress = {
  client: "complete";                         // Project always has a clientId
  project: "complete";                        // the Project itself exists
  property: "complete" | "incomplete";        // properties.length > 0
  spaces: "complete" | "incomplete";          // spaces list total > 0
  workItems: "complete" | "incomplete";       // work-items list total > 0 (scoped to project)
};
```

Computed in a small pure function from the already-fetched
Property/Spaces/WorkItems query results (each already needed by their own
tabs) — not a new endpoint, not persisted anywhere. The Overview page
renders the four steps with ✓/○ and links into `property`, `spaces`,
`work-items` tabs; the user may navigate directly to any tab regardless of
prior steps' completeness (resumable, not a gated wizard), matching
architecture §14's explicit "not a cross-module mega-wizard" requirement.

## 11. Malaysia-First Formatting

## 12a. Shared Test Infrastructure

**MSW (Mock Service Worker)** intercepts HTTP at the network layer (not by
mocking `fetch`/`client.ts` internals), so tests exercise the real
`openapi-fetch` client, the real `client.ts` bearer-injection/401 logic, and
real TanStack Query cache behavior against realistic request/response
shapes generated from the same `schema.ts` types the app uses.

- `src/test/server.ts` — `setupServer(...defaultHandlers)` from `msw/node`.
- `src/test/handlers.ts` — one default handler per F1 endpoint (success
  cases matching the schemas in §2), imported by `server.ts` and overridden
  per-test via `server.use(...)` for error/edge cases (e.g. the F1.8 `409`
  cancelled-WorkItem case, F1.2's failing-refresh case).
- `vitest.setup.ts` — `beforeAll(() => server.listen())`,
  `afterEach(() => server.resetHandlers())`, `afterAll(() => server.close())`.
- `src/test/renderWithProviders.tsx` — the **shared isolated test-provider
  wrapper** every component/integration test uses instead of RTL's bare
  `render()`:

```tsx
export function renderWithProviders(
  ui: React.ReactElement,
  { route = "/", queryClient = createQueryClient() } = {}
) {
  // pushes `route` into a test router (e.g. next-router-mock or an
  // in-memory MemoryRouter-equivalent for App Router hooks), wraps `ui` in
  // <QueryClientProvider client={queryClient}><AuthProvider>...
  // </AuthProvider></QueryClientProvider> — the SAME nesting order as the
  // real Providers component (§5a) — and returns RTL's render() result
  // plus the queryClient instance for assertions that need it.
}
```

Because `queryClient.ts` exports a factory (§5a correction), every call to
`renderWithProviders` gets a fresh, isolated `QueryClient` by default —
no cross-test cache leakage, and a test that needs to assert on cache state
directly can still pass its own pre-seeded instance.

This infrastructure is built once in F1.0/F1.1 (handlers grow incrementally
as each feature checkpoint adds its own), not deferred to F1.10.

     the 401s in the first place — the test controls precisely when and
     how many 401s occur.
